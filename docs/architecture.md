# 一人指挥多角色 Agent · 系统设计

## 1. 一句话

用户只面对一个对话框（微信/飞书），背后是一支有分工、有记录、有验收标准的 Agent 团队。

## 2. 分层

```
┌─────────────────────────────────────────────────────┐
│  L1 入口层    微信 / 飞书 机器人（@xmanrui/dsh-im）    │
│               一个对话框，用户只说人话                   │
├─────────────────────────────────────────────────────┤
│  L2 指挥层    Team Lead（指挥官）                       │
│               拆需求 · 定优先级 · 分派 · 验收 · 合并      │
├─────────────────────────────────────────────────────┤
│  L3 角色层    产品经理 / 架构师 / 数据 / 前端 / 评审 / 文档 │
│               每个角色一个 Agent，独立上下文              │
├─────────────────────────────────────────────────────┤
│  L4 执行层    Worktree Space（一任务一空间）             │
│               每个任务一条分支，互不干扰                   │
├─────────────────────────────────────────────────────┤
│  L5 记录层    OpenSpec（proposal → specs → tasks → archive）│
│               需求、方案、任务、验收标准全部留痕            │
├─────────────────────────────────────────────────────┤
│  L6 存储层    GitHub 远程仓库                           │
│               代码 + 文档 + 规格，可回溯、可协作            │
└─────────────────────────────────────────────────────┘
```

## 3. 一次需求的完整旅程

```
用户微信：「收入分析要能看到每个门店的客流和客单价下钻」
   │
   ▼
指挥官：判断为「新功能」→ 开一个 OpenSpec change
   │
   ▼
产品经理：写 proposal.md（为什么、做什么）
          写 specs/（需求 + 场景 + 验收标准）
   │
   ▼
指挥官：把 proposal 摘要回给用户 → 用户回「可以」
   │
   ▼
架构师：写 design.md（数据模型、接口、页面结构）→ 拆 tasks.md
   │
   ▼
指挥官：建 Worktree Space，分派
   ├─ 数据工程师 → 指标计算 + 接口
   └─ 前端工程师 → 页面 + 图表
   │
   ▼
评审官：跑测试、对验收标准、提问题
   │
   ▼
指挥官：合并 → 推 GitHub → 归档 change（archive）
   │
   ▼
用户微信：收到「已完成，这是预览地址」
```

## 4. 为什么这样设计

| 问题 | 传统做法 | 这套做法 |
|---|---|---|
| 需求失忆 | 微信里翻聊天记录 | OpenSpec 里每个 change 有 proposal + specs，永久可查 |
| 改乱了 | 一个 Agent 全干，上下文越滚越脏 | 每个角色独立上下文，只拿自己需要的 |
| 无法并行 | 串行等 | Worktree Space 一任务一空间，真并行 |
| 质量靠感觉 | 没有验收标准 | specs 里写死场景，评审官逐条对 |
| 代码丢失 | 本地一堆副本 | GitHub 单一远程，分支可回溯 |
| 用户看不懂 | 日志、diff | 微信里说人话；`openspec view` 有仪表盘 |

## 5. 关键机制

### 5.1 角色隔离

每个角色只拿三样东西：任务书、相关规格、相关代码路径。不共享全量上下文。

### 5.2 任务的三种形态

- **小改**：指挥官直接做，不进 OpenSpec。
- **新功能**：必须走 OpenSpec change（proposal → specs → tasks）。
- **修 bug**：直接改 + 补测试，不强制 OpenSpec。

### 5.3 验收闸门

合并前必须过三关：
1. specs 里的场景逐条通过；
2. 构建 + 测试通过；
3. 评审官没有阻塞意见。

### 5.4 用户可见性

用户不需要懂 git。他只需要知道：
- 现在在做什么（一句话）
- 卡在哪（如果有）
- 什么时候能看（预览地址）

## 6. 技术选型（Demo 阶段）

| 层 | 选择 | 理由 |
|---|---|---|
| 前端 | Next.js 15 + TypeScript + Tailwind + shadcn/ui | 商用可延续，组件生态全 |
| 图表 | ECharts | 瀑布图、漏斗图、下钻都成熟 |
| 数据 | SQLite（better-sqlite3）+ 种子数据 | 零运维，Demo 足够，后续可换 PG |
| 数据源 | 从现有 Excel 抽取样例 | 真实感强，讲解能对上 |
| 部署 | Docker + 本地预览；后续 Vercel/阿里云 | Worktree Space 支持 Docker 冒烟验收 |
| 规格 | OpenSpec | 需求即文档，文档即验收 |
| 协作 | GitHub | 代码与规格同仓 |

## 7. 与商用目标（6 万/套）的关系

Demo 阶段只做**收入分析模块**，但骨架按商用设计：

- 多租户字段预留（brand / company）
- 数据导入抽象层（Excel / API / 手工）
- 指标引擎与页面解耦（换页面不换算法）
- 权限模型预留（总部 / 区域 / 门店）
- 报告导出（PDF / PPT）留接口

7 天只验证一件事：**这套分析逻辑 + 这个交互形态，用户愿不愿意付费。**
