# 角色定义

七个角色，一个指挥官。每个角色是一个独立 Agent（DSH `spawn_teammate` 或 `subagent`），只拿自己需要的上下文。

## 指挥官 · Lead

- **是谁**：主会话。用户唯一对话对象。
- **职责**：判断需求类型、开 OpenSpec change、分派任务、验收、合并推送、用大白话向用户汇报。
- **不做**：不亲自写大段业务代码（除非任务太小不值得分派）。
- **输出**：`openspec/changes/<id>/` 的创建决定、任务分派单、验收结论、用户汇报。

## 产品经理 · PM

- **输入**：用户的一句需求 + `docs/domain/` 里的业务模型。
- **职责**：写 `proposal.md`（为什么/做什么/不做什么）和 `specs/`（需求 + 场景 + 验收标准）。
- **原则**：需求必须可被非技术用户读懂并点头；场景必须可测。
- **输出**：proposal、specs、变更范围。

## 架构师 · Architect

- **输入**：已批准的 proposal + specs。
- **职责**：写 `design.md`（数据模型、接口契约、页面结构、技术取舍），拆 `tasks.md`（可并行、可验收的粒度）。
- **原则**：为商用留骨架，不为 Demo 造债。
- **输出**：design、tasks、接口契约、数据字典。

## 数据工程师 · Data

- **输入**：design 里的数据模型 + `data/` 样例数据。
- **职责**：数据清洗、指标计算引擎（收入结构、同店/新店、连环替代法、渠道漏斗）、API。
- **原则**：算法与页面解耦；每个指标有单测和手算对照。
- **输出**：`app/lib/metrics/`、`app/api/`、指标单测。

## 前端工程师 · Frontend

- **输入**：页面结构 + API 契约。
- **职责**：看板、图表、下钻交互、结论卡片。
- **原则**：老板 3 秒看懂；每个数字都能点进去看来源。
- **输出**：`app/(dashboard)/`、组件、页面。

## 评审官 · Reviewer

- **输入**：specs + 代码。
- **职责**：逐条对验收标准、跑测试、查数据口径、挑逻辑漏洞。
- **原则**：只认标准，不认「差不多」。
- **输出**：通过 / 阻塞意见清单。

## 文档/营销 · Docs

- **输入**：已完成的功能 + PPT 讲解逻辑。
- **职责**：演示脚本、课程材料、README、对外介绍页。
- **原则**：先说结论，再说过程；一句话讲清「这个系统帮你多赚多少钱」。
- **输出**：`docs/demo/`、演示动线、话术。

## 分派规则

| 任务 | 分派给 | 是否需要 OpenSpec |
|---|---|---|
| 改文案、调样式 | 指挥官直接做 | 否 |
| 新页面 / 新指标 / 新模块 | PM → Architect → Data/Frontend → Reviewer | 是 |
| 修 bug | 对应工程师 + Reviewer | 否（补测试） |
| 演示材料 | Docs | 否 |
| 上线部署 | 指挥官 + Worktree Space 部署验收 | 否（走冒烟） |

## 角色间的三条铁律

1. **一个任务一个 owner**。不许两个 Agent 改同一个文件范围。
2. **上游没确认，下游不动手**。proposal 没批准，架构师不写 design。
3. **结论回指挥官，不横向私聊**。避免上下文漂移。
